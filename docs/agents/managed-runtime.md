# pi for IDE 托管运行时与版本管理设计

> 状态：已实施（扩展 0.1.7 起生效，本文件是当时的决策记录）。
> 范围：`vscode-extension` 侧的服务器组件解析、安装、升级、多版本共存
> 与清理。不含 pi-web 包内部实现。
>
> 后注：进程生死主权后来整体转向 web 侧（attach 而非 own、deactivate
> 不杀进程、watchdog 自收割）——那套演化见 `embed-protocol.md`，
> 本文档的 §6"重启本窗口 server"等表述仍有效但语义以那边为准。

## 1. 背景与问题

### 当时的项目状态（本设计的出发点）

- VSIX 已瘦身为纯外壳：扩展不内嵌 pi-web，运行时靠解析链从
  外部安装（全局 npm / 托管目录 / npx）。
- 托管安装是**平铺单目录**：`globalStorage/runtime/node_modules/<pkg>`，
  所有版本共用一处，升级 = `npm i` 原地覆盖。
- 扩展宿主**按窗口一实例**（每开一窗一个 extension host），
  `globalStorage` 却全实例共享；autoStart 开启时重启恢复多窗
  几乎同时触发安装与版本选择。
- embed 握手当时只有"404 vs 200"的探测，没有兼容性表达。
- 尚无 attach/watchdog：每窗自 spawn 自 stop，进程归属按
  "谁拉起谁负责"理解。

四类问题都在这个状态下被实测暴露：

1. **原地升级与运行中进程的文件锁冲突**（npm `EBUSY`）。
   Windows 对运行中进程的工作目录与已加载文件持有句柄；
   平铺布局下 `npm i` 升级必须重命名/替换同一个
   `node_modules` 子树——server.js 正在跑的目录被改名必炸，
   稳定复现；POSIX 不报错但同样会留下半写状态。
   → 解法（§4）：版本目录物理隔离，运行目录与安装目标永不相交。
2. **版本兼容性**。两侧独立发版（扩展走商店、包走 npm），
   任一侧都可能先动；embed 契约当时只能在 spawn 后握手
   才发现不兼容——下载+启动完才告警属坏体验。
   → 解法（§2/§5）：`piIde.level` 阶梯把兼容判断提前到
   解析/安装时，可装可不装的版本也能区分。
3. **多窗口/多编辑器共存**。共享 `globalStorage` 遇上按窗一实例：
   两窗并发 `npm i` 同一目录（部分写入互踩）、marker 覆盖写、
   一窗升级动到另一窗正在运行的文件。
   → 解法（§4/§6）：原子安装锁 + marker 只向前翻 +
   版本目录隔离运行文件。
4. **版本堆积**。改为版本目录布局后每次升级落一份
   （每份数百 MB），无清理规则则无界增长。
   → 解法（§7）：低于 marker 且无进程占用的可判清理。

## 2. 兼容性模型（共享"特性级别"整数）

核心是一个两侧共享的**单调整数**（沿用 embed 协议号语义，
表示"桥接功能阶梯"的档位，非营销版本号）：

- **包侧声明**：发行包 `package.json` 携带
  `"piIde": { "level": <int> }`——该版本实现、且要求宿主具备的
  级别。字段缺失视为 1（已发布版本均无字段且实现 v1）。
- **扩展侧声明**两个界：
  - `EMBED_PROTOCOL_SUPPORTED`：扩展当前实现的级别（只增）。
  - `MIN_PKG_LEVEL`：仍被支持的最低包级别——**下线历史特性时
    抬高它**，向后兼容不是义务而是可退役的策略。
- **闸门**（安装/选择时判）：
  `MIN_PKG_LEVEL ≤ pkg.piIde.level ≤ SUPPORTED`。
  - `level > SUPPORTED` → 需要更新的扩展（见 §6 needsExtensionUpgrade）
  - `level < MIN_PKG_LEVEL` → **硬底线**：包已低于本扩展支持范围，
    不是"建议升级"而是必须用兼容包才能运行——强制升级包；
    ≥下限且兼容集内有更新 → 软提示，由用户选择是否升级
- **运行时校验**：`/api/embed` 握手回报级别（保留现状，
  最后一道防线，不兼容仅告警）。
- 级别只在桥接功能真正变化时递增；可选增量特性（对端忽略
  未知 kind）不构成级别提升。级别与版本号的对应关系只在文档
  层面维护，不作为机制。

## 3. 解析链（维持顺序，语义不变）

```
piIde.executablePath → 内置 resources（过渡残留）
→ npm root -g 全局包 → PATH shim（pi-web-for-ide，校验包名）
→ 托管运行时（§4，缺则现场装）→ npx（过渡兜底，待移除）
```

任何腿解析出的 bin，其包 `package.json.piIde.embedProtocol`
超出支持区间时：记日志 + 跳过该腿继续向下（托管腿按 §5 的规则
从已装版本里另选），不静默启动不兼容副本。

## 4. 目录布局与版本选择

```
<globalStorage>/runtime/
  current-version            # 文本，唯一真相：当前生效版本
  .installing                # 跨窗口安装锁（原子创建）
  versions/<ver>/node_modules/<pkg>/   # 每版本一目录
  node_modules/<pkg>/        # 0.1.7 前旧式平铺（视为最旧版本，可清除）
```

- **版本选择（启动/解析时）**：
  1. marker 指向的版本 → bin 存在且协议兼容 → 用之；
  2. 否则按版本降序扫 `versions/*`，取第一个 bin 存在且兼容者；
  3. 否则旧式平铺存在且兼容 → 用之；
  4. 否则触发托管安装（§6，装注册表中**最高兼容版本**）。
- marker 写入只在安装成功后；指向损坏/缺失/不兼容版本时
  按上一条重新选择（marker 不自愈改写，避免并发窗口互相覆盖）。

## 5. 版本比较与"最高兼容版本"

- 注册表查询一次拿全包文档（`versions` 映射含每版本的
  `piIde.level`），过滤 `MIN_PKG_LEVEL ≤ level ≤ SUPPORTED`
  后按版本比较取最大。
- 版本比较沿用现有的 `X.Y.Z[-N]` 预发版感知比较器。
- **结果三态**：
  - `best`：最高兼容版本（升级/安装目标）；
  - `needsExtensionUpgrade`：latest 的 level > SUPPORTED——
    提示"先升级 pi for IDE 扩展"（扩展无法自我升级，
    更新经扩展商店完成），**不**安装不兼容包；
  - `none`：无任何兼容版本可用——明示失败。

## 6. 安装与升级

- `installManagedPackage(pkg, ver)`：`npm i --prefix
  versions/<ver> pkg@ver --ignore-scripts` → 成功且 bin 存在 →
  写 marker → 触发 §7 清理。
- **跨窗口互斥**（三级防线）：
  1. `.installing` 原子锁串行化安装动作；后到者等待装完复用，
     残留 >10min 按失效清理；
  2. marker 只**向前翻**（新 > 旧才写）——后到者发现 marker
     已是目标版本即返回"已最新"，不会出现倒车覆盖；
     人工降级走 `管理服务器版本` 命令，不受此限；
  3. 运行中 server 与安装目录物理隔离（版本目录），升级全程
     不动兄弟窗口的运行文件。
- **升级动作**（命令 `pi for IDE: 升级服务器组件` + 检查通知按钮
  走同一路径）：
  1. 查注册表 → 得 §5 三态；
  2. `best > current` → 确认后装进 `versions/<best>`；
  3. 翻 marker → **只重启本窗口 server**（树杀自有子进程后重解析）；
     兄弟窗口继续跑旧目录，重启时自然切到 marker 新版——
     全程不动运行中文件，故无 EBUSY。
- **新版生效路径**：marker 翻转即刻决定"下一次解析"的目标；
  本窗口升级后提示重启，重启 = 树杀旧进程→重解析→新 bin；
  面板收到新 URL 自动重连（shell serverReady→探测→iframe 换址），
  会话状态随服务器进程重开（pi 会话持久在磁盘不受影响）。
  兄弟窗口无需通知：各自下次启动即新版。
- 全局安装腿沿用包管理器原地升级（其锁风险由"用户自管安装"
  的定位承担，文案提示先停服务）。

## 7. 旧版本清理

**原则**：低于当前生效版本且无运行占用的目录可删；高于或
不兼容但可能在未来可用的高版本保留。

| 对象 | 判定 | 动作 |
|---|---|---|
| `versions/<ver>`，`ver < marker` | 无进程命令行含该路径 | 删 |
| `versions/<ver>`，`ver >= marker` | — | 保留（含协议不兼容的高版本） |
| marker 版本 | — | 永不删 |
| `node_modules/`（旧式平铺） | 版本化布局存在且无占用 | 删 |
| 有进程占用的任何目录 | — | 跳过，下次再清 |

触发点：激活时 + 每次成功安装后（尽力而为，失败静默留待下次）。

## 8. 用户命令面

| 命令 | 用途 |
|---|---|
| `pi for IDE: 升级服务器组件` | §6 编排：检查→确认→装新版→重启 |
| `pi for IDE: 管理服务器版本` | 兜底面板：列出已装版本（当前/兼容/
  不兼容标注），支持切换 marker 与单项清理 |

其余（启动/停止/打开/提及）不变。

## 9. 代码组织（重构）

- `src/managedRuntime.ts`（新）：布局/marker/锁/registry 兼容查询/
  版本选择/版本目录安装/版本清理——版本管理单一归宿。
- `src/piIdeServer.ts`：进程生命周期（解析链编排、spawn/stop、
  embed 握手、诊断、端口扫描、孤儿清扫）——托管细节下沉到新模块。
- `src/extension.ts`：命令注册与 UX 编排。
- `src/webviewProvider.ts`：面板 shell 与消息转发（本轮不变）。

## 10. 明确不做 / 边界

- 不自动杀"疑似我们的"非 `_npx` 进程（可能是有意的独立运行）；
  `_npx` 孤儿仍由激活清扫处理。
- 不为回退保留上一版本：marker 回退场景用重装覆盖。
- 不做自动升级：检查通知只告知，升级始终经用户确认。
